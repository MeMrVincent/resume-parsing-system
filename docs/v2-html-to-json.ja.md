# HTML/Web → JSON 処理フローの説明

[English](v2-html-to-json.md) | [简体中文](v2-html-to-json.cn.md) | **日本語**

> このドキュメントは V2（word/xls/pdf/html → JSON）の流れを説明します。ディレクトリの既定値はルートの `config.example.json` を参照してください。本文中の `<プロジェクトルート>` は config の project_root のことです。統合した重複スクリプトは [`v2-name-mapping.ja.md`](v2-name-mapping.ja.md) の末尾にあります。

## 1. 目的と範囲

このフローは、Web ページ、メールのアーカイブ、HTML 風の履歴書を統一された履歴書 JSON に変換し、元ファイル、ステージングファイル、JSON のフィールド、多言語版をファイルごとにレビューして差分で修復します。

処理の範囲は、`32718文件报告.xlsx`（32,718 ファイルの棚卸しレポート）の `Web网页与邮件 (.html, .eml)` ワークシート（Web ページとメール）で決まり、特定のディレクトリや特定のバッチで切り出すことはしません。現在対応している主な拡張子は次のとおりです：

```text
.html  .htm  .mht  .mhtml  .eml
```

基本原則：

- 元の Web ファイルは読み取り専用で、名前の変更・移動・上書き・削除をしてはいけない；
- ステージングファイルは元ファイルとバイト単位で一致させ、SHA-256 で検証する；
- HTML／メールの本文がフィールドの事実の出所であり、「フィールドに値がある」だけで合格と判断してはいけない；
- JSON はルートの `CONTEXT.md` が定めるフィールド、スナップショット、多言語の規約に従う；
- 毎回、先に問題を記録し、次に差分で修復し、最後に全件を再レビューする；
- 業務 JSON には `repair_history`、`rounds` などの肥大化する監査履歴を保存しない；
- 各レコードの状態、問題、修復の操作は、外部の `_*.v2.json` レポートにまとめて保存する。

## 2. ディレクトリと正本ファイル

| 内容 | パス |
| --- | --- |
| ファイル棚卸しレポート | `<プロジェクトルート>\32718文件报告.xlsx` |
| JSON フィールドの正本の仕様 | `CONTEXT.md`（リポジトリには公開していません。フィールド構造は `examples/` のサンプル JSON を参照） |
| 元の Web ファイル | `<プロジェクトルート>\需要采集的简历文件夹` とそのサブディレクトリ |
| Web の安全なステージングディレクトリ | `<プロジェクトルート>\complete-transfered-htmls\web\input` |
| Web 変換のメインマップ | `<プロジェクトルート>\complete-transfered-htmls\web\web_conversion_map.v2.json` |
| 正式な業務 JSON | `<プロジェクトルート>\complete-transfered-jsons\web` |
| 全件の独立レビューレポート | `<プロジェクトルート>\complete-transfered-jsons\web\_web_full_review.v2.json` |
| 全件の差分修復レポート | `<プロジェクトルート>\complete-transfered-jsons\web\_web_full_repair.v2.json` |
| ファイル名とフラット化のレポート | `<プロジェクトルート>\complete-transfered-jsons\web\_web_output_organize.v2.json` |

`web_conversion_map.v2.json` は元ファイル単位のメインインデックスです。ワークブックの行、元ファイルのパス、ステージングのパス、元ファイルのハッシュ、JSON のパス、状態、検査結果は、すべてこれを基準に結び付けられます。ファイル名から元ファイルと JSON の対応を推測してはいけません。

正式ディレクトリの業務 JSON はすべてフラットに置きます。ファイル名の形式は次のとおりです：

```text
氏名_携帯番号.json
氏名_メール.json
氏名_无联系方式.json       # 「无联系方式」＝連絡先なし
氏名_携帯番号_2.json       # 同じ氏名・連絡先のファイルが複数あるときは連番を増やす
```

ファイル名は携帯番号を優先し、携帯番号がなければメールを使い、どちらもなければ `无联系方式` を使います。`_` で始まる JSON はレポートであり、候補者の業務 JSON ではありません。

## 3. ファイル間の関係

```text
32718文件报告.xlsx
        │ 全件の範囲と元の絶対パスを定める
        ▼
web_conversion_map.v2.py
        │ 元ファイル 1 件につき 1 レコードを作成・維持する
        ├──────────────► web_conversion_map.v2.json
        │                         │
        │ 読み取り専用でコピーし   │ source/stage/json の対応を提供
        │ ハッシュを検証           │
        ▼                         ▼
complete-transfered-htmls/web/input  web_html_to_json.v2.py
                                          │
                                          ▼
                           complete-transfered-jsons/web/*.json
                                          │
                         ┌────────────────┴────────────────┐
                         ▼                                 ▼
              web_full_review.v2.py              web_json_audit.v2.py
            独立した読み取り専用の全件レビュー      基本監査／状態の書き戻し
                         │
                         ▼
                 _web_full_review.v2.json
                         │ 問題一覧が修復の入力になる
                         ▼
                 web_full_repair.v2.py
                  フィールドごとの差分修復
                         │
                         ├────────► _web_full_repair.v2.json
                         │          各レコードの最終状態
                         ▼
                 web_full_review.v2.py
                    再度の全件確認
                         │
                         ▼
                web_output_organize.v2.py
      ファイル名の検証、フラット化、古いコピーの片付け
```

関係の説明：

1. ワークブックが「どの物理ファイルを処理すべきか」を決める。
2. マップが「ある行がどの元ファイル、ステージングファイル、JSON に対応するか」を決める。
3. ステージングファイルは元のバイト列を保持し、変換器はステージングファイルから本文を読む。
4. 業務 JSON は正規化したデータを保存し、毎回の長い監査履歴は保存しない。
5. review レポートは修復前後の問題を記録し、repair レポートはマップの各オブジェクトの状態と修復の操作を記録する。
6. organize レポートは最終的なファイル名、移動の結果、正確に削除した古いコピーを記録する。

## 4. 第 1 段階：Web の全件マップの作成

### `python/v2/web_conversion_map.v2.py`

このプログラムはワークブックの Web ワークシートを読み、履歴書でないと最終判断されたもの、連絡先のないもの、元ファイルに異常のあるものも含めて、すべての行を残します。元ファイルを安全なステージングディレクトリにコピーして内容のハッシュを計算し、元のファイルには手を触れません。

実行：

```powershell
cd <プロジェクトルート>
python python\web_conversion_map.v2.py
```

ワークブックの範囲や元ファイルが変わったときだけ `--force` を使います：

```powershell
python python\web_conversion_map.v2.py --force
```

注意：`--force` はステージングファイルを再コピーし、状態を再計算します。すでに修復を行ったバッチでは軽々しく実行しないでください。確認済みのマップの状態が初期状態で上書きされるのを避けるためです。

## 5. 第 2 段階：Web/HTML → JSON

### `python/v2/web_html_to_json.v2.py`

Web の HTML 風ファイルから JSON への、現在の正式な入口です。次を担当します：

- `.html`、`.htm`、`.mht`、`.mhtml`、`.eml` を読み込む；
- MHTML/EML のメール本文をデコードする；
- 51job、智聯、猎聘と、一般の HTML 履歴書を解析する；
- 基本情報、求職希望、職歴、学歴、資格、言語、スキル、研修、プロジェクトを抽出する；
- `CONTEXT.md` が定める JSON 構造を生成する；
- 純粋な英語または日本語の元ファイルでは、本物のフィールド単位の中国語の `resumes[0]` を生成し、元の言語の版を後ろの resume に残す；
- JSON をアトミックに書き込み、マップに書き戻す。

全件変換：

```powershell
python python\web_html_to_json.v2.py --limit 0
```

指定したワークブック番号だけを再実行：

```powershell
python python\web_html_to_json.v2.py --indices 300 650 1559 --force
```

再現できるランダムサンプリング：

```powershell
python python\web_html_to_json.v2.py --random --limit 50 --seed 20260804
```

`--force` は、明確に再構築が必要なレコードにだけ使います。一括で上書きする前に、必ず修復前のレポートを保存し、問題の証拠を失わないようにします。

## 6. JSON 構造の要件

トップレベルは次のとおり固定です：

```text
schema_version
record_id
source
extraction
dates
classification
structured_data
raw_text
quality
```

`structured_data` は次のとおり固定です：

```text
base_info
expected_info
current_info
education_info
resumes
```

このうち：

- `base_info`、`expected_info`、`current_info`、`education_info` は `resumes[0]` のトップレベルのスナップショット；
- すべての経歴リストは `structured_data.resumes[]` にだけ存在してよい；
- `raw_text` は JSON のトップレベルにだけ存在してよい；
- リストの項目に余分なフィールドがあってはならない；
- 日付は統一形式でなければならない。例：`2013年03月01日`；
- `school_degree_rank` は文字列 `"1"` ～ `"7"` か空文字列のみ；
- `resume_languge` は `CONTEXT.md` の正式な綴りをそのまま使う。

業務 JSON に次のものを書き込んではいけません：

```text
repair_history
rounds
```

この 2 種類の履歴は JSON のサイズを急速に膨らませます。毎回の問題と修復状態は外部レポートに書いてください。

## 7. 多言語のルール

多言語の順序は統一しなければなりません：

```text
resumes[0].resume_languge = "zh"
resumes[1].resume_languge = "en" または "jp"
```

厳格な要件：

- `resumes[0]` はフィールド単位の中国語の内容でなければならず、英語や日本語のオブジェクトの言語ラベルを `zh` に変えるだけではいけない；
- 外国語の会社名、学校名、職種、専攻、職務内容、資格などは、すべて中国語の主版に翻訳する；
- 後ろの外国語の resume は元の言語の内容を保持する；
- 同じ経歴は、各言語版でリストの件数、順序、日付、意味が対応していなければならない；
- 多言語のオブジェクトはディープコピーとし、2 つの resume が同じオブジェクトを参照して互いに上書きしてはならない；
- 外国語の原文が 1 版だけの場合は、まず元の言語の版としてコピーし、その後で中国語の翻訳版を生成する。

専用ツール：

### `python/v2/web_multilingual_repair.v2.py`

全件レビューのレポートでマークされた多言語の問題だけを処理します。ローカルのオフライン翻訳を使って中国語の主版を修復し、元の言語の版を保持します。

```powershell
python python\web_multilingual_repair.v2.py
```

実行後は必ず `web_full_review.v2.py` を再度実行します。翻訳プログラム自体が正常終了したことを、データが合格した証拠としてはいけません。

## 8. 厳格な意味のルール

フィールドに値があることは、そのフィールドが正しいことを意味しません。レビューと修復では、「値が何か」と「その値がそのフィールドに属するか」の両方を確認しなければなりません。

### 職歴

次のものは正式な職歴として扱いません：

- インターン、見習い、intern、trainee；
- サークル、学生会、学内の協会、学内のアルバイト；
- 単独のリサーチアシスタント、課題研究、卒業論文；
- 研修、語学力、特技などの章の見出し；
- 会社名の位置に入った職務内容の文、業界、給与、連番の断片。

同じ会社・同じ日付が「業界／給与の行 + 職種の行」に解析されている場合は、1 件の本物の職歴に統合します。

### 学歴

- `school_name` は学校または教育機関でなければならず、専攻、スキル、場所、研修コース、章の見出しであってはならない；
- 1 件の学歴が「学校の 1 件 + 学位の 1 件」に分かれている場合は統合する；
- サークル、在学中のアルバイト、短期研修、卒業研究は正式な学歴にできない；
- 開始・終了の時期が同じでも重複とは限らず、ダブルディグリーの可能性もあるため、学校とほかのフィールドを比べて判断する。

### 資格と認証

資格の名称は、明確な資格、免許、認定、試験の等級を指していなければなりません。次のものは削除するか、作り直さなければなりません：

- 場所。例：「上海」「日本」；
- 学校、研修機関、認証会社の名称；
- 「証書」「研修証書」などの章の見出しや汎用的な語；
- 「現在は……審査員」のような状態の文。元の文に基づいて明確な資格名に作り直す；
- 「份考试」のような途切れたテキスト；
- 優秀卒業生、奨学金、コンテストの賞、優秀論文などの栄誉；
- 職務内容、実験の手配、活動の説明。

例：

```text
誤り：目前为OHSMS审核员        （現在は OHSMS 審査員）
正解：职业健康安全管理体系（OHSMS）国家注册审核员        （労働安全衛生マネジメントシステム（OHSMS）国家登録審査員）

誤り：方圆标志认证集团有限公司        （方圓標誌認証集団有限公司）
対応：削除する。研修／認証機関であって資格ではない
```

### スキル、言語、研修、プロジェクト

- `skills_list` を単語や句読点で分割してはならない；
- English／日本語などの言語は `language_list` に入れる；
- CET、TEM、JLPT、IELTS などの資格は、言語資格または資格リストに入れる；
- 研修機関、コース名、資格名を互いにずらしてはならない；
- インターン、サークル、卒業論文を、プロジェクトや研修に見せかけて残してはならない。

## 9. 第 3 段階：全件の独立レビュー

### `python/v2/web_full_review.v2.py`

このプログラムは業務 JSON、マップ、ステージングファイル、元ファイルを読むだけで、独立したレポートを書き出します。本番の変換ロジックが正しいことを示すために本番の変換ロジックを import することはしないため、最終的な品質ゲートになります。

```powershell
python python\web_full_review.v2.py
```

既定のレポート：

```text
complete-transfered-jsons/web/_web_full_review.v2.json
```

検査する内容：

- ワークブックとマップが 1 対 1 に対応しているか；
- 元ファイル、ステージングファイル、ハッシュが一致しているか；
- JSON のパス、元ファイルのパス、ファイルサイズが正しいか；
- トップレベルとすべてのリストのフィールドが `CONTEXT.md` に厳密に合っているか；
- トップレベルのスナップショットが `resumes[0]` と一致しているか；
- フィールドの値が元の文章に証拠として見つかるか；
- 多言語の版が揃っているか、翻訳とリストが対応しているか；
- 会社、学校、職種、資格、スキルに意味のずれがないか；
- インターン、サークル、学内の協会、研究などの主要でない内容が残っていないか；
- 孤立した JSON、重複した出力、空の元ファイルがないか。

ある回の修復前のレポートを保存するときは、別のファイル名を使い、上書きしてはいけません：

```powershell
python python\web_full_review.v2.py `
  --report complete-transfered-jsons\web\_web_review_round_before.v2.json
```

## 10. 第 4 段階：差分修復

### `python/v2/web_full_repair.v2.py`

このプログラムは review レポートを読み、マップのすべてのレコードを再検査し、信頼できる元ファイルの証拠がある問題のフィールドだけを変更して、各オブジェクトの最終状態を外部の repair レポートに書き込みます。

```powershell
python python\web_full_repair.v2.py
```

ある回の修復前レポートと、独立した修復レポートを指定する：

```powershell
python python\web_full_repair.v2.py `
  --review complete-transfered-jsons\web\_web_review_round_before.v2.json `
  --report complete-transfered-jsons\web\_web_repair_round.v2.json
```

状態の意味：

| 状態 | 意味 |
| --- | --- |
| `clean` | 今回の検査で問題がなく、変更もなし |
| `repaired` | 今回差分の変更を行い、再確認後に残る問題はない |
| `needs_review` | 自動修復の後も問題が残っている |
| `no_json_expected` | 履歴書でない、連絡先がないなど、JSON を生成しないのが想定どおり |
| `failed` | 元ファイルがない、空、または読み取れず、JSON を確実には生成できない |

修復が終わったら、必ず全件レビューを再実行します。推奨するループ：

```text
review（修復前レポートを保存）
  → repair（今回の修復レポートを保存）
  → review（最終レポートを更新）
  → まだ問題があれば次の回へ
```

レポートをゼロにするために、フィールドを一括で空にしてはいけません。元の文章から復元できる内容は作り直し、汚染・ずれ・主要でない内容だと確実に言える場合だけ削除します。

## 11. その他の補助プログラム

| ファイル | 役割 | メインフローとの関係 |
| --- | --- | --- |
| `python/v2/web_json_audit.v2.py` | HTML/JSON/マップの基本監査。`--apply` で監査状態を書き戻せる | 補助的な検査で、full review の代わりにはならない |
| `python/v2/web_html_json_reconcile.v2.py` | 初期の JSON ごとの突き合わせプログラム | 互換用のツール。現在のメインフローでは full review を優先する |
| `python/v2/web_html_json_repair.v2.py` | 初期の、reconcile の結果に基づく修復 | 互換用のツール。埋め込み式の長い履歴を再び書き込んではならない |
| `python/v2/web_batch_report.v2.py` | マップからバッチの統計レポートを再構築する | 集計のみで、業務データは修復しない |
| `python/v2/web_internship_boundary_recovery.v2.py` | かつての intern/International の境界の不具合からの復旧を記録する | 専用の過去の検証ツール |
| `python/v2/web_output_organize.v2.py` | ファイル名を確認し、出力をフラット化し、マップを更新し、検証済みの古いコピーを片付ける | 内容の問題をすべて解消した後に実行する |

これらの補助プログラムは、「full review が最終的な独立した品質ゲートである」という原則を変えてはいけません。

## 12. ファイル名の検証とフラット化

### `python/v2/web_output_organize.v2.py`

まずレビューだけを行う：

```powershell
python python\web_output_organize.v2.py
```

`collision_count = 0`、`needs_review = 0` になって初めて適用できる：

```powershell
python python\web_output_organize.v2.py --apply
```

適用時にプログラムは次を行います：

- 氏名と実際の連絡先から最終的なファイル名を生成する；
- 同じ氏名・連絡先の複数のファイルには `_2`、`_3` を付ける；
- 分類サブディレクトリ内の JSON を `complete-transfered-jsons/web` の直下に移す；
- マップ内の `json_path` を更新する；
- 古いファイルと現在マップに対応しているファイルで `record_id + source.path` がともに一致する場合だけ、古いコピーを削除する；
- 不明なファイル、レポートファイル、一意に対応付けられない JSON は削除しない。

JSON を手作業で一括移動してからマップを直すことはしないでください。元ファイル、JSON、レポートの結び付きが失われます。

## 13. 推奨する全件再実行の順序

```powershell
cd <プロジェクトルート>

# 1. ワークブックや元ファイルの範囲が変わったときだけマップを再構築する

# 2. JSON を生成する、または対象を絞って再構築する
python python\web_html_to_json.v2.py --limit 0

# 3. 修復前の全件の問題を保存する
python python\web_full_review.v2.py `
  --report complete-transfered-jsons\web\_web_review_round_before.v2.json

# 4. 差分修復

  --review complete-transfered-jsons\web\_web_review_round_before.v2.json `
```

## 14. よくある問題と対処

### JSON のフィールドに値はあるが、意味が明らかに誤っている

元の文章とフィールドの意味を基準にします。会社が職務内容の文であってはならず、学校が「特技」であってはならず、資格が場所や機関であってはなりません。まず review レポートに正確なパスと値を記録してから、差分で修復します。

### 英語の履歴書の `resumes[0]` も英語になっている

これは誤りです。`resumes[0]` は完全な中国語訳であるべきで、`resumes[1]` が `en` の原文を保持します。日本語も同様です。

### 同じ職歴が 2 件に解析されている

会社、開始時期、終了時期、職種を比べます。1 件が業界／給与の断片で、もう 1 件が本物の職種であれば統合します。単に空でない 2 件のレコードを残すことはしません。

### 資格リストに優秀卒業生、論文、研修機関が入っている

これらは資格ではありません。栄誉は現行の業務ルールに従って削除します。研修機関は研修レコードの機関フィールドに残します。審査員の試験に明確に合格し資格を得ている場合は、元の文章に基づいて完全な資格名に作り直します。

### 元ファイルはあるが 0 バイト

不合格の元ファイルと判定し、状態を `failed / source_file_empty` と記録します。中身のない JSON を生成してはならず、ファイル名から内容を推測してもいけません。空でない元のファイルが改めて入手できて初めて復旧できます。

### review レポートはゼロなのに、人の目ではまだ問題が見つかる

まず、レビューのルールがすべての `resumes` とリストを本当に走査しているかを確認します。特にインデント、早すぎる `return`、握りつぶされた例外、空のリストだけを検査しているといった、網羅の抜けに注意します。ルールを追加した後は、利用者が例に挙げたファイルだけでなく、1,739 件すべての業務 JSON に対してレビューを再実行しなければなりません。

### JSON ファイルがどんどん大きくなる

業務 JSON に `repair_history` や `rounds` を誤って書いていないかを確認します。監査履歴は外部レポートに保存しなければなりません。削除した後は、入れ子のオブジェクトの中にもこの 2 つのキーがないことを全件スキャンで確認します。

## 16. v2 の命名と保守の取り決め

- 現在の Web メインフローの実装とコマンドラインの入口は、すべて `*.v2.py` を使う；
- `web_html_to_json.v2.py` は、ドット付きの v2 の依存先を実行時に読み込む；
- バージョン番号のないファイルや `_v2.py` の過去のファイルは、互換用の土台としてのみ使い、新しい Web バッチの入口にしてはならない；
- レビュー、修復、専用のスクリプトを追加するときは、引き続き `web_<用途>.v2.py` を使う；
- 新しいルールは、まず独立した review に入れてから repair に入れる。生成器の中だけで黙って修正してはならない；
- フィールド構造を変更する前に、まず `CONTEXT.md` を更新し、その後で変換器、レビュー器、修復器、説明ドキュメントを同期させる；
- 業務 JSON に書き込むプログラムはすべて、アトミックな書き込みを守り、完了後に JSON が解析できることを検証する。
