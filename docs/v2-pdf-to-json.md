# PDF to JSON v2 Description

**English** | [简体中文](v2-pdf-to-json.cn.md) | [日本語](v2-pdf-to-json.ja.md)

> This document describes the V2 (word/xls/pdf/html → JSON) flow. Default directories are in `config.example.json` in the repository root; `<project root>` in the text is `project_root` in config. The duplicate scripts that were merged are listed at the end of [`v2-name-mapping.md`](v2-name-mapping.md).

## 1. Goal and principles

This flow turns PDF résumés into `complete-v1` candidate JSON, finally published to:

```text
<project root>\complete-transfered-jsons\pdf\new
```

The current baseline is **PDF v2**. It does not generate the final JSON directly from the PDF text layer. Instead it uses:

```text
Original PDF
  + Word converted by iLovePDF
  + path and classification notes in PDF文档.json
  + GPT / old JSON as reference
      ↓
Word → semantic HTML → per-source JSON → per-candidate merged JSON → semantic repair → double audit → publish to new
```

Historically, extracting directly from the PDF text layer gave poor structural quality for complex tables, two-column layouts, Japanese-style résumé forms and multilingual résumés. The Word files produced by iLovePDF usually preserve tables and paragraphs better, so Word is the primary parsing input; the original PDF is always kept as the basis for checking identity, text, page count and layout.

Core principles:

1. The original PDF is the final evidence; never modify or overwrite it.
2. Word is the primary parsing input, but where Word and PDF conflict, the visible PDF content prevails.
3. GPT JSON and old JSON are reference only and must not unconditionally override the source files.
4. Each physical PDF first produces one per-source JSON, which is then merged by candidate identity.
5. The same name is not an automatic basis for merging; strong evidence such as mobile number and e-mail comes first.
6. Nothing is published to `new` until the full audit passes.

## 2. Directory responsibilities

### 2.1 Input and notes

```text
<project root>\complete-transfered-htmls\pdf\
├── input\                  Original PDFs
├── word\                   DOCX generated by iLovePDF or re-converted by hand
└── PDF文档.json            PDF paths, classification and manual notes
```

- `input`: original PDFs, including résumés and a few non-résumé files.
- `word`: the results of PDF-to-Word conversion; file names may have been changed by hand, so matching cannot rely on file names alone.
- `PDF文档.json`: the authoritative manual information — original path, whether it is a résumé, candidate notes, contact details, HTML name, etc.

### 2.2 JSON references and formal output

```text
<project root>\complete-transfered-jsons\pdf\
├── old\                    Low-quality products of the previous round; reference only
├── gpt\                    Reference JSON converted by ChatGPT or merged by hand
└── new\                    The current formally delivered JSON
```

- `old`: must not be treated as correct data directly.
- `gpt`: part of it is of good quality, part has duplicates, multilingual structure differences or wrong merges; use it only when identity and source counts match.
- `new`: atomically replaced only after all candidate-level audits pass.

### 2.3 Intermediate products and reports

```text
<project root>\complete-transfered-htmls\pdf\
├── rebuild-work\
│   ├── pdf_rebuild_map.v2.json       Authoritative map
│   ├── html\                         Semantic HTML converted from Word
│   ├── json-by-source\                Per-source staging, one JSON per PDF
│   └── json-by-candidate\             Candidate-level merged staging
└── rebuild-reports\                   Extraction, audit, merge, review and publication reports
```

## 3. Current v2 code

The main PDF flow uses only the following 13 entries:

| File | Responsibility |
|---|---|
| `python/v2/pdf_rebuild_map.v2.py` | Builds the authoritative map of PDF, Word, manual notes, GPT and old JSON |
| `python/v2/pdf_rebuild_extract.v2.py` | Word → semantic HTML → per-source JSON |
| `python/v2/pdf_rebuild_audit.v2.py` | Audits per-source JSON against the map for coverage, identity, structure and source hash |
| `python/v2/pdf_rebuild_merge.v2.py` | Conservative merge by candidate; multilingual versions are kept independently |
| `python/v2/pdf_rebuild_semantic_repair.v2.py` | Removes field misplacement, template placeholders, HTML leaks, duplicates and work/education misclassification, and loads the manually verified PDF overrides |
| `python/v2/pdf_raw_text_v2.py` | Rebuilds independent source-text evidence from Word, PDF and semantic HTML, cleans transcoding noise and de-duplicates by physical source |
| `python/v2/pdf_rebuild_candidate_audit.v2.py` | Audits candidate-level JSON and confirms each source is covered exactly once |
| `python/v2/pdf_json_strict_audit.v2.py` | Compatibility structure audit; checks snapshots, dates and basic source evidence |
| `python/v2/pdf_json_field_strict_audit.v2.py` | Publication gate: per language, per list and per field, checks placeholder values, field misplacement, entity misclassification, dates, contact details, duplicates, source evidence and the completeness of the independent `raw_text` |
| `python/v2/pdf_rebuild_finalize.v2.py` | Atomically publishes to `new` after the audit passes |
| `python/v2/pdf_rebuild_issue_table.v2.py` | Generates the issue table of Word files to be re-converted by hand / hard-to-recognize files |
| `python/v2/pdf_gpt_review_compare.v2.py` | Runs a four-way comparison of PDF, Word, GPT and the current JSON on GPT structure differences |
| `python/v2/pdf_gpt_review_resolve.v2.py` | Incrementally writes manual review conclusions into the persistent override file |

The following shared code is still reused; it does not belong to the deleted old PDF pipeline:

- `c_resume_html_dom_common.v2.py`: Word HTML DOM handling.
- `c_resume_html_to_json_common.v2.py`: general résumé field parsing and schema normalization.
- `xls_to_html_to_json.v2.py`: XLS grid enhancement rules for Japanese-style table Word files.

## 4. Complete run steps

All commands are run under `<project root>`.

### 4.1 Build the map

```powershell
python python/v2/pdf_rebuild_map.v2.py
```

The map stage does the PDF/Word inventory, links the manual classification, matches same names and content aliases, links GPT/old references, analyses PDF page counts and text layers, and isolates non-résumés.

Key files:

```text
rebuild-work/pdf_rebuild_map.v2.json
rebuild-reports/pdf_word_aliases.v2.json
rebuild-reports/pdf_pilot_30.v2.json
```

### 4.2 Full extraction

```powershell
python python/v2/pdf_rebuild_extract.v2.py `
  --scope all `
  --force `
  --report complete-transfered-htmls/pdf/rebuild-reports/pdf_full_extract.v2.json
```

Processing order:

1. read the matching DOCX;
2. convert to standard Word HTML;
3. decide whether it is plain Word, a Word table or a Japanese-style table;
4. plain Word uses the heading, paragraph, date and entity rules;
5. Japanese-style tables first reuse the XLS grid semantic rules;
6. when the XLS enhancement cannot safely handle a language/date format, fall back to the standard Word HTML;
7. output the per-source JSON;
8. add source file, date, identity and classification information from the PDF and manual notes.

Extraction statuses include:

- `success`: the structure is clear;
- `needs_review`: the per-source parse has weak points, but they can later be filled in from other versions of the same candidate or from the reviewed GPT Chinese version;
- `non_resume`: clearly not a résumé;
- `failed`: reading or conversion failed; must not enter the candidate merge.

### 4.3 Per-source audit

```powershell
python python/v2/pdf_rebuild_audit.v2.py `
  --report complete-transfered-htmls/pdf/rebuild-reports/pdf_full_audit.v2.json
```

It must be confirmed that every résumé that should be processed has a per-source JSON, there are no surplus JSON files, source SHA-256 and paths agree, identity and structure meet the minimum requirements, and non-résumés have not entered the candidate data.

### 4.4 Candidate-level merge

```powershell
python python/v2/pdf_rebuild_merge.v2.py --replace
```

Merge rules:

1. The same mobile number or the same e-mail is strong evidence for merging.
2. A matching name is only supporting evidence; when contact details conflict hard, do not merge.
3. Chinese, Japanese, English, German, etc. are stored separately in `structured_data.resumes`.
4. For the same language, prefer the version with a complete structure and a reliable source; do not simply concatenate non-empty lists.
5. Multiple sources only fill in empty fields; a poorer version never overrides an existing reliable field.
6. GPT Chinese is enabled only when the GPT file, the number of source files and the candidate identity agree.
7. GPT repairs that have passed the four-way review are loaded persistently from `pdf_gpt_review_overrides.v2.json`.

### 4.5 Semantic repair

```powershell
python python/v2/pdf_rebuild_semantic_repair.v2.py `
  --root complete-transfered-htmls/pdf/rebuild-work/json-by-candidate `
  --apply
```

This stage handles company/school/position misplacement, template headers, HTML fragments, duplicate experiences, reversed dates and wrong splitting of single-source multilingual résumés. Individual cases confirmed by visual verification against the original PDF are stored in `rebuild-reports/pdf_semantic_overrides.v2.json` and are still reused in later full re-runs.

### 4.6 Candidate coverage and all-field strict audit

```powershell
python python/v2/pdf_rebuild_candidate_audit.v2.py `
  --json-root complete-transfered-htmls/pdf/rebuild-work/json-by-candidate

python python/v2/pdf_json_field_strict_audit.v2.py `
  --json-root complete-transfered-htmls/pdf/rebuild-work/json-by-candidate
```

Before publication the following must hold:

- `missing_source_hashes` is empty;
- `duplicate_source_hashes` is empty;
- each résumé source is covered by exactly one candidate JSON;
- `quality:ready` equals the total number of candidates;
- pending translations are 0;
- GPT structures pending review are 0;
- quality warnings are 0.
- The strict audit's `strict_failure_file_count`, `review_file_count` and `total_issue_count` are all 0.

"Strict" does not mean only checking that fields are non-empty. The auditor re-reads the PDF, Word and HTML in the map as independent evidence and checks field by field:

- whether entities such as name, phone, e-mail, company, school, position and major can be traced back to the source text;
- whether schools, companies, projects, certificates, languages and self-evaluation have been put in the wrong list;
- whether entity fields contain section titles, template text, long duty paragraphs or dates;
- whether the date format, chronological order, employment status, education level and enumerated values are reasonable;
- whether the same list contains exact or semantic duplicate records;
- whether multilingual versions keep their own structure and agree with the source file of the corresponding language;
- whether the top-level snapshots agree with the Chinese primary version;
- whether `raw_text` was rebuilt independently from the source files, and whether the source blocks, hashes, lengths and text coverage are correct;
- whether it contains `WordOOXMLTable*`, OpenXML table markers, HTML fragments, C0/C1 control characters or common transcoding garble.

### 4.7 Publication

```powershell
python python/v2/pdf_rebuild_finalize.v2.py --replace
```

The publisher first copies to a temporary directory and verifies the SHA-256 of each file; only when all pass does it atomically replace:

```text
<project root>\complete-transfered-jsons\pdf\new
```

After publication the all-field audit must be run once more on the formal directory, to avoid the staging directory and the formal directory being inconsistent:

```powershell
python python/v2/pdf_json_field_strict_audit.v2.py `
  --json-root complete-transfered-jsons/pdf/new `
  --report complete-transfered-htmls/pdf/rebuild-reports/pdf_json_field_strict_audit.formal.v2.json `
  --csv complete-transfered-htmls/pdf/rebuild-reports/pdf_json_field_strict_audit.formal.v2.csv
```

Finally also check `pdf_finalization.v2.json`: `published_count` should be 419 and `map_resume_records_updated` should be 561, and compare the staging and formal directories by the SHA-256 recorded for each file in the report; the hash difference must be 0.

## 5. Japanese-style table résumés

Files whose names or contents contain markers such as "日语, 日文, 履歴書, 職務経歴書" usually use a table layout. Common risks include:

- year, month and school/company scattered in different cells;
- "enrolment" and "graduation" recognized as two education entries;
- education, work and qualifications in the same large table;
- Chinese entity names mixed with Japanese headings;
- one file containing both a 履歴書 and a 職務経歴書.

The v2 handling strategy:

1. restore the real cell grid from the DOCX OOXML;
2. convert Word tables into XLS-style two-dimensional cells;
3. reuse the XLS rules for horizontal fields, event rows and language layers;
4. re-bind name, contact details, work, education and qualifications;
5. if the XLS-enhanced result is incomplete or a rule fails, keep the standard Word HTML, so that the enhancer never interrupts the full batch;
6. finally still check the number of entries, dates and classification against the table visible in the PDF.

## 6. GPT difference review

After merging, if `pdf_gpt_translation_review.v2.json` is not empty, run:

```powershell
python python/v2/pdf_gpt_review_compare.v2.py
```

The four-way material is the full pages of the original PDF, the iLovePDF Word / semantic HTML, the GPT JSON and the current candidate JSON. Pay special attention to multilingual duplicates, schools mistaken for companies, projects/certificates mistaken for work, Japanese-style enrolment/graduation splits and wrong merges of several résumés.

After confirmation, add the conclusion to `FACTS` in `pdf_gpt_review_resolve.v2.py`, then run:

```powershell
python python/v2/pdf_gpt_review_resolve.v2.py
python python/v2/pdf_rebuild_merge.v2.py --replace
python python/v2/pdf_rebuild_candidate_audit.v2.py
```

The review script is incremental: existing review records are kept, and new records are appended or replaced by GPT file path, so a full re-run does not bring back structures that have already been fixed.

## 7. When Word needs to be re-converted

In the following cases the item goes into the issue table and a person re-converts the Word:

- the Word is empty or contains only images;
- the PDF clearly has content but the Word lacks pages;
- table rows and columns are badly misaligned;
- name, contact details or main experience are lost in the Word;
- the PDF is a scan and iLovePDF did not OCR it correctly;
- the Word and the PDF are not the same content.

Generate the issue table:

```powershell
python python/v2/pdf_rebuild_issue_table.v2.py
```

After a person replaces the Word, the PDF is not modified. Example of incrementally re-extracting given files:

```powershell
python python/v2/pdf_rebuild_map.v2.py
python python/v2/pdf_rebuild_extract.v2.py `
  --filenames "file-to-rerun.pdf" `
  --force `
  --report complete-transfered-htmls/pdf/rebuild-reports/pdf_reextract_batch.v2.json `
  --merge-into-report complete-transfered-htmls/pdf/rebuild-reports/pdf_full_extract.v2.json
python python/v2/pdf_rebuild_audit.v2.py `
  --report complete-transfered-htmls/pdf/rebuild-reports/pdf_full_audit.v2.json
python python/v2/pdf_rebuild_merge.v2.py --replace
python python/v2/pdf_rebuild_semantic_repair.v2.py --apply
python python/v2/pdf_rebuild_candidate_audit.v2.py
python python/v2/pdf_json_field_strict_audit.v2.py
python python/v2/pdf_rebuild_finalize.v2.py --replace
```

## 8. JSON structure requirements

Candidate JSON contains at least `schema_version`, `record_id`, `source.source_files`, `dates`, `extraction`, `classification`, `structured_data.base_info`, `structured_data.resumes`, the experience lists, `raw_text` and `quality`.

Rules:

1. `resumes[0]` is preferably the Chinese primary version.
2. `expected_list`, `work_experiences`, `education_list`, `certificate_list`, `language_list`, `skills_list`, `training_list`, `project_list` and `communication_list` may appear only inside each `structured_data.resumes[]`; these lists must not be copied under the main object.
3. Only the four query snapshots `base_info`, `expected_info`, `current_info`, `education_info` and `resumes` remain at the top level of `structured_data`; the snapshots are kept consistent with the Chinese primary version.
4. Each work, education, project and training item must be one entry per segment; empty entity records must be deleted.
5. Every structured value must conform to the definition of that field in the context document; having a value alone is not enough to count as qualified; the value must be semantically reasonable and traceable to the corresponding source document.
6. Do not stuff a whole passage of source text into a company name, school name, position, major, project name or certificate name, and do not treat a school as a company, a company as a school, or campus experience as work.
7. Do not keep template or conversion placeholder values such as `公司名称` ("company name"), `学校名` ("school name"), `Post/Wages`, `WordOOXMLTable*`.
8. High-school, technical-secondary, junior-high and primary-school experiences do not enter `education_list`; university, junior-college, bachelor's, master's, doctoral, etc. map degree and education type according to the context specification.
9. Language exams go into `language_list`; the exam name or level is written to `language_level`, and `language_certificate` may only be `有` (yes), `无` (no) or an empty string.
10. Dates of month precision are normalized to `YYYY年MM月01日`; full-width digits, Chinese-numeral years and forms like `YYYY～YYYY` must be standardized, but a month or specific day that the source document does not give must not be invented. "Until now" is expressed by an empty end date and `status=在职` (currently employed).
11. After merging multilingual résumés, every physical source must appear in `source.source_files` and `source.merge_trace`, recording at least file name, path, SHA-256, language and document type, for traceability.
12. `raw_text` is completely decoupled from the final structured fields. Each physical source is delimited with `===== SOURCE: file name =====`; the multiple and multilingual résumés of one person are merged by source into one `raw_text`, de-duplicated by file name, SHA-256 and body text, so that each source appears only once.
13. For a single source block, Word text is the first candidate; when Word is unusable, use the PDF, then supplement with semantic HTML the lines that are missing from Word/PDF and not duplicated. Clean-up is limited to table-conversion markers, HTML metadata, control characters, reversible transcoding garble and definite duplicate aggregate lines; content that is hard to read but belongs to the original must not be deleted for the sake of looks.
14. It is forbidden to splice or back-fill `raw_text` from structured fields such as `base_info`, work, education, projects and certificates. Even if a structured name, phone number or translated entity does not appear in the text layer, it must not be written into `raw_text` to make the audit pass.
15. `extraction.raw_text_source` is fixed as `canonical_deduplicated_pdf_word_html_text`; the strict audit independently re-reads the PDF, Word and HTML and checks the source declaration, the number of source blocks, length, duplicates and text coverage.

Individual cases confirmed by hand are stored in:

```text
<project root>\complete-transfered-htmls\pdf\rebuild-reports\pdf_semantic_overrides.v2.json
```

This file is applied after cross-language reconciliation and is the final authoritative override layer. When adding an override, the source-file basis must be recorded at the same time, so that the next full re-run does not bring back the old error.

## 11. Rules for later version upgrades

The current v2 is the only valid PDF implementation. When developing v3 later:

1. copy the current v2 scripts as v3; do not overwrite v2 directly;
2. the code files, `VERSION`, the default MAP and the report file names must all be upgraded together;
3. v3 uses an independent staging area or clearly versioned reports, to avoid polluting the v2 acceptance baseline;
4. run a small pilot batch first, then the full run;
5. compare source coverage, candidate count, quality status and the structure of key candidates;
6. replace the formal `new` only after the v3 full audit passes;
7. decide whether to delete the old version only after the upgrade is complete; two entries with the same name must never coexist.
